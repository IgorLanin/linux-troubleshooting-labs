# Инцидент №4: невозможность входа в систему - после успешной аутентификации сессия завершается


Цель: научиться диагностировать и устранять проблемы при входе в систему, когда пользователь успешно проходит аутентификацию, но сессия сразу же завершается.
Инструменты: tail, journalctl, getent.


Как воспроизвести инцидент:
1. Выполнить следующие команды (в рамках скрипта будет предложено придумать имя нового пользователя и пароль, для которого будет воспроизведен инцидент):
- `chmod +x ~/linux-troubleshooting-labs/scripts/lab_4/incident_4.sh`
- `~/linux-troubleshooting-labs/scripts/lab_4/incident_4.sh`

2. После запуска скрипта добавьте исключение для созданного пользователя, чтобы для него была разрешена аутентификация по паролю в `/etc/ssh/sshd_config` на сервере, после чего нужно перезапустить `sshd` сервис.

Пример того, что нужно добавить в конец файла (подставьте имя созданного пользователя вместо `new_user`:

``` bash
Match User new_user
    PasswordAuthentication yes
```

3. Попробуйте сделать несколько попыток входа на сервер по ssh с рабочей машины от имени нового пользователя.

4. После завершения работы с инцидентом, удалите созданного пользователя.

# [Не могу зайти на сервер по SSH](/incidents/tickets/INC-008.md)

Краткое описание инцидентa (симптомы): пользователь не может зайти на сервер по SSH. Сообщает, что вводит пароль правильно, но войти не получается - сессия завершается и система просит ввести учетные данные снова.


Источник инцидента: тикет от пользователя



Таймлайн инцидента:
- 25.05.2026 14:00:00 - Проблема возникла
- 25.05.2026 15:10:00 - Создан тикет в системе
- 25.05.2026 15:23:00 - Начата диагностика
- 25.05.2026 15:31:00 - Найдена причина
- 25.05.2026 15:35:00 - Инцидент устранен



Диагностика:
1. `tail -f /var/log/auth.log` или `journalctl -u ssh` - есть логи о том, что аутентификация успешная, после чего сессия завершается
2. `getent passwd username` - пользователь существует и в качестве shell установлена `/bin/false`
3. `cat /etc/shells` - shell `/bin/false` отсутствует в списке


Первопричина:
- У пользователя установлена shell, которого нет в списке доступных. 


В каких случаях это может произойти: 
- Пользователь мог установить пакет с другой shell (например, `zsh`). После установки в `/etc/passwd` она изменится и, если удалить `zsh` и не поменять shell обратно на одну из установленных (например, `/bin/bash`), то останется запись с несуществующей shell. Это приведет к login loop (успешная аутентификация и спустя секунду завершение сессии и предложение ввести учетные данные снова)
- Ошибка настройки системным администратором



Что проверить в реальной работе, если с shell все в порядке:
- Место на диске: проверить `df -h`
- Доступы (у пользователя нет доступа к своему домашнему каталогу или файлам): проверить `ls -la ~username`
- Config-файлы ssh (запрещен ли вход пользователю, ограничен ли доступ по IP, есть ли ошибки в `sshd_config`): проверить `/etc/ssh/sshd_config` и config-файлы в `/etc/ssh/sshd_config.d/`
- PAM: искать `pam_unix` в `/var/log/auth.log`, проверить pam-конфиги `cat /etc/pam.d/sshd`
- Проверяем, заблокирован ли пользователь: `faillock --user username`



Решение:
- Поменять shell: `sudo usermod -s /bin/bash username`
- Попросить пользователя попробовать войти на сервер по ssh снова
