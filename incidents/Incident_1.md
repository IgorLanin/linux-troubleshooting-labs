# Группа инцидентов №1: система работает медленно и не отвечает


Цель: отработка диагностики инцидентов Linux (CPU, disk, service, logs)
Инструменты: top/htop, df, journalctl, systemctl


Воспроизвести нижеуказанные инциденты выполнив следующие команды на сервере:
1. `chmod +x ~/linux-troubleshooting-labs/scripts/incident_1.sh`
2. `~/linux-troubleshooting-labs/scripts/incident_1.sh`

После завершения работы с инцидентами, можно устранить инциденты с помощью скрипта, если инциденты не были устранены вручную:
1. `chmod +x ~/linux-troubleshooting-labs/scripts/fix_incident_1.sh`
2. `~/linux-troubleshooting-labs/scripts/fix_incident_1.sh`


В рамках данной группы инцидентов могут быть сгенерированы следующие тикеты на основании сработавших алертов в системе мониторинга:

1. [Alert-001 - Disk full](/incidents/tickets/alert-001.md)
2. [Alert-002 - Service down](/incidents/tickets/alert-002.md)
3. [Alert-003 - CPU overload](/incidents/tickets/alert-003.md)

Разберу каждый алерт отдельно и составлю отчеты.





# 1. [Alert-001 - Disk full](/incidents/tickets/alert-001.md)

Краткое описание инцидентa: закончилось место на диске.

Источник инцидента: Система мониторинга (Grafana)

Сработавшие алерты:
- disk_used_percent > 90%


Влияние на сервис:
- Проблемы с записью новых данных на диск
- Падение сервисов


Таймлайн инцидента:
- 18.05.2026 10:21:10 - Сработал alert disk_used_percent > 90%
- 18.05.2026 10:22:00 - Создан тикет в системе
- 18.05.2026 10:25:00 - Начата диагностика
- 18.05.2026 10:30:00 - Найдена причина
- 18.05.2026 10:33:00 - Инцидент устранен


Диагностика:
1. `df -h`: диск `/dev/sdb` заполнен на 96% (общий размер диска: 2GB)
2. `df -i`: inode не израсходованы
3. `sudo du -xh /test_mount | sort -rh | head -n 4`: директория `/test_mount/load/` занимает 1.8GB
4. `sudo find /test_mount/load -type f -exec du -h {} + | sort -rh | head -n 20`: файл `/test_mount/load/bigfile` занимает 1.8GB
5. `stat`: дата создания файла 10:19:58
6. `tail -f `оследние строки содержимого файла


Первопричина:
- Был создан файл `/test_mount/load/bigfile`, который занимает почти все свободное пространство на диске.


Решение:
- Т.к. файл `/test_mount/load/bigfile` не содержит важную информацию, файл был удален.

В реальной работе порядок действий зависит от ситуации и может быть следующим:
1. Сделать перед исправлением первопричины:

- Почистить`/tmp` `/var/tmp`;
- Почистить package cache: `apt clean all`
- Почистить/удалить старые логи: `/var/log`, `journalctl --vacuum-time=7d`;

2. Устранить первопричину

3. Сделать backup/archive

4. Расширить хранилище



Как предотвратить инцидент в будущем:
- Обращать внимание на создаваемые файлы и следить за свободным пространством на диске.



Итоговый статус: Инцидент решён (Resolved)





# 2. [Alert-002 - Service down](/incidents/tickets/alert-002.md)

Краткое описание инцидентa: nginx в статусе inactive более 2 минут.

Источник инцидента: Система мониторинга (Grafana)

Сработавшие алерты:
- service_status != running for 2m


Влияние на сервис:
- Сервис не активен


Таймлайн инцидента:
- 18.05.2026 10:25:03 - Сработал alert service_status != running for 2m
- 18.05.2026 10:27:00 - Создан тикет в системе
- 18.05.2026 10:30:00 - Начата диагностика
- 18.05.2026 10:35:00 - Найдена причина
- 18.05.2026 10:33:00 - Инцидент устранен



Диагностика:
1. `sudo systemctl status nginx`: сервис в статусе `inactive (dead)`
2. `sudo journalctl -xeu nginx`: был послан сигнал `SIGTERM`, сервис был деактивирован.



Первопричина:
- Был послан сигнал `SIGTERM`, сервис был деактивирован.

В реальной работе:
1. Быстро восстановить работу сервиса
2. Найти первопричину и устранить ее (проблема с config-файлом / диск загружен / проблемы с CPU)
3. Настроить перезапуск сервиса автоматически в `nginx.service`, добавив в config следующее (если не было сдалано раньше):

``` bash
[Service]
Restart=on-failure
RestartSec=5
```

Решение:
- Перезапуск сервиса: `sudo systemctl restart nginx`


Как предотвратить инцидент в будущем:
- Настроить перезапуск сервиса автоматически


Итоговый статус: Инцидент решён (Resolved)





# 3. [Alert-003 - CPU overload](/incidents/tickets/alert-003.md)

Краткое описание инцидентa: Высокая нагрузка CPU более 5 минут.

Источник инцидента: Система мониторинга (Grafana)

Сработавшие алерты:
- avg(cpu_usage_idle) < 5% for 5m


Влияние на сервис:
- Паденние производительности, замедление работы сервера


Таймлайн инцидента:
- 18.05.2026 10:23:03 - Сработал alert avg(cpu_usage_idle) < 5% for 5m
- 18.05.2026 10:22:00 - Создан тикет в системе
- 18.05.2026 10:25:00 - Начата диагностика
- 18.05.2026 10:30:00 - Найдена причина
- 18.05.2026 10:33:00 - Инцидент устранен


Диагностика:
1. `top/htop`: два процесса полностью загружают CPU
2. `strace -p pid` - посмотрю, что эти процессы делают.


В реальной работе порядок действий зависит от ситуации и мне нужно будет найти ответы на следующие вопросы:
- Что за процесс грузит CPU?
- Почему он грузит процесс и нормальное ли это поведение?
- Как он был запущен?
- Какой родительский процесс его запустил?
- Это баг или ожидаемая рабочая нагрузка?


Первопричина:
- Были созданы два процесса, которые постоянно пишут `yes`, создавая нагрузку на систему.


Решение:
- `sudo kill -9 pid_process_1 pid_process_2`


Как предотвратить инцидент в будущем:
- Мониторинг
- Исправление багов
- Оптимизация архитектуры


Итоговый статус: Инцидент решён (Resolved)
